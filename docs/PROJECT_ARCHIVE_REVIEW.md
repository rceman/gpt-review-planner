# Project Archive Review

This is the canonical guide for preparing and reviewing an attached code-project
archive. It supports arbitrary languages, frameworks, and repository layouts.

## Supported entry modes

1. **Prepared pinned archive** — preferred for recurring projects. The archive
   contains `.gpt-workflow.lock` and managed `AGENTS.md`; the lock identifies an
   immutable workflow commit.
2. **Raw archive plus immutable prompt URL** — valid for first-time or external
   projects. No lock is required initially; the exact immutable prompt revision
   is used and the missing lock is reported, never fabricated.
3. **Already integrated project** — read and validate the existing lock. Do not
   update workflow integration unless the owner explicitly requests it.

## Workflow authority order

Resolve authority in this order:

1. current explicit owner instructions;
2. approved task-specific specifications and ADRs in the project;
3. a valid `.gpt-workflow.lock` in the supplied project;
4. an immutable workflow tag or commit explicitly supplied by the owner;
5. the exact immutable revision containing the invoked prompt.

A stale, malformed, or unreachable lock is an integrity issue. Never silently
fall back to `main`, `latest`, or another mutable ref.

## Task objective

The owner may request a full review, bug discovery, refactoring, performance
improvement, dependency audit, security review, architecture review,
test-coverage review, a specific feature/correction, or the highest-value next
work. The objective controls review depth and proposed scope. Without one,
perform a complete static project review. Surface independent critical blockers
or security defects, but do not broaden an implementation patch without owner
approval.

## Deliverable modes

### Default review-to-patch mode

Review the archive, produce prioritized findings and an exact proposed patch
scope, then stop for explicit owner approval. After approval, create an
Executable Patch Pack using the canonical patch-pack workflow.

### Review-only mode

Return analysis, findings, and patch decomposition only. Do not implement
production or test changes and do not create an Executable Patch Pack.

## Lock lifecycle

`.gpt-workflow.lock` is generated by `setup.sh` or updated by `update.sh`; it is
not hand-authored. The owner selects an immutable workflow tag or exact commit,
and the preparation agent passes that value explicitly. Archive preparation uses
a staging copy by default so the source repository is not modified merely to
create an upload. Source integration is a separate explicit operation.

A reviewer must not mutate a raw archive merely to manufacture a lock. A valid
lock is read and validated; a missing lock is reported while the immutable
prompt URL remains sufficient authority for that review.

## Recommended invocations

Raw archive:

```text
Review the attached project archive using this immutable guide:

<IMMUTABLE_ARCHIVE_REVIEW_PROMPT_URL>

Task objective:
<OWNER_TASK_OBJECTIVE_OR_FULL_REVIEW>

Use the default review-to-patch workflow.
Stop after the proposed exact patch scope and wait for my approval.
```

Prepared archive:

```text
Prepare this project for GPT archive review using:

<IMMUTABLE_ARCHIVE_PREPARATION_PROMPT_URL>

Use staging mode and pin the owner-selected immutable workflow revision.
```

Integrated archive:

```text
Review the attached archive using the workflow pinned by its
`.gpt-workflow.lock`.

Task objective:
<OWNER_TASK_OBJECTIVE_OR_FULL_REVIEW>

Stop after the proposed exact patch scope and wait for my approval.
```

Immutable tag or commit URLs are preferred over `main`; copying complete prompts
manually is unnecessary. Raw archives with an immutable prompt URL are valid,
prepared archives are preferable for recurring projects, and official tooling
generates locks rather than reviewers.

## Archive preparation contract

The local coding agent may prepare a staging archive containing project source,
a generated valid lock, and the managed planner block. It must exclude `.git`,
dependency directories, build outputs, caches, runtime artifacts, IDE/OS
metadata, secrets, private keys, and unrelated binaries while preserving
intentionally versioned fixtures and required assets. It reports source revision,
archive root, file count, size, SHA-256, exclusions, and deviations.

Dirty source worktrees stop by default. Including dirty changes requires an
explicit owner request and an accurate dirty-state report. Existing mismatched
locks stop unless an explicit workflow update is authorized.
